## Relationships

### Core Sales Tables

| Table A | Column A | Table B | Column B | Relationship |
|---|---|---|---|---|
| sales_opportunity | accountid | sales_account | id | Deal -> owning Account |
| sales_opportunity | ownerid | sales_user | id | Deal -> Opportunity Owner (rep) |
| sales_account | ownerid | sales_user | id | Account -> Account Owner |
| sales_user | managerid | sales_user | id | Self-join: Rep -> their Manager |
| sales_account | parentid | sales_account | id | Self-join: Child -> Parent Account |

### Sales ↔ Finance Bridge (the "Waterfall" logic)

| Table A | Column A | Table B | Column B | Relationship / Match Priority |
|---|---|---|---|---|
| sales_account | client_id_c | financial_cp_portfolio_lead_mapped | mm_id | Step 1 (most reliable) - ID match |
| sales_account | name | financial_cp_portfolio_lead_mapped | sf_client_name | Step 2 - verified SF spelling match |
| sales_account | name | financial_cp_portfolio_lead_mapped | client_entity | Step 3 - direct entity name match |
| sales_opportunity | company_group_c | financial_cp_portfolio_lead_mapped | operational_group | Step 4 (last resort, group-level only) |

Steps 1-3 apply to specific account attribution (Use Case B). All 4 steps apply to broad group/entity classification (Use Case A) — stop at the first step that returns a match.

### Finance Tables ↔ Central Mapping Sheet

All finance tables join back to financial_cp_portfolio_lead_mapped using client_name (and mm_id where available) as the key:

| Table A | Column A | Table B | Column B |
|---|---|---|---|
| financial_mm_actual_backlog | client_name | financial_cp_portfolio_lead_mapped | client_name |
| financial_mm_actual_backlog | mm_id | financial_cp_portfolio_lead_mapped | mm_id |
| financial_mm_fy27_plan | client_name | financial_cp_portfolio_lead_mapped | client_name |
| financial_mm_target_with_portfolio_fy27 | client_name | financial_cp_portfolio_lead_mapped | client_name |
| financial_db_actual_backlog | account | financial_cp_portfolio_lead_mapped | client_name |
| financial_db_actual_backlog | mm_id | financial_cp_portfolio_lead_mapped | mm_id |
| financial_db_fy27_plan_target | account | financial_cp_portfolio_lead_mapped | client_name * |
| financial_taktical_actual_backlog | client_name | financial_cp_portfolio_lead_mapped | client_name |
| financial_taktical_actual_backlog | mm_id | financial_cp_portfolio_lead_mapped | mm_id |
| financial_td_fy27_plan_target | client | financial_cp_portfolio_lead_mapped | client_name * |

\* DB and TD Plan & Target sheets only have a cumulative monthly Target across all clients (per the reference notes) — they don't break down Target at the client level like Mediamint does, so joins to those rows are mainly useful for Plan figures, not Target attribution per client.

### Key Notes on the Relationships

- mm_id is the most reliable join key wherever it's populated — it directly links sales_account.client_id_c to every finance table's mm_id/client_name field via the mapping sheet.
- client_entity in the mapping sheet serves double duty: it rolls up subsidiary companies under one parent for reporting, and acts as a fallback match key against sales_account.name.
- operational_group in the mapping sheet is the field that ultimately decides whether a client/deal counts under Mediamint, DataBeat, or Taktical for entity-level rollups.
- Only Mediamint's target table (financial_mm_target_with_portfolio_fy27) has true client-level Target detail — DB and TD only break out Target at the aggregate/cumulative level.
